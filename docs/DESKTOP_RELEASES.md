# Desktop releases

The browser app remains a standalone local-first site. This document covers only the signed desktop release path; it does not change browser storage, hosting, or product boundaries.

## Version contract

Use SemVer without a `v` prefix. Update the same value in `package.json`, `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`, then run:

```powershell
bun run version:check
```

The command fails if any of the three values drift.

## Signed local build

Tauri verifies updates with a public key embedded only in a signed-release build. Development, no-bundle checks, and ordinary local installers intentionally omit that overlay, so an explicit update check reports that updates are unavailable instead of accepting unsigned content.

Generate a key once in a secure directory outside this repository, retain it securely, and never commit it:

```powershell
bun run tauri -- signer generate --ci --write-keys <secure-directory>/updater.key
```

Set the private key path or contents and the generated public-key contents only in your current environment. Keep a second protected recovery copy outside the repository.

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = '<secure key path or contents>'
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = '<secure key password>'
$env:TAURI_UPDATER_PUBLIC_KEY = '<public key contents>'
bun run desktop:release
```

`desktop:release` creates a temporary ignored Tauri overlay, enables updater artifacts, uses only `https://github.com/ifBars/mod-description-workbench/releases/latest/download/latest.json`, and removes the overlay after the build. It never prints the key. If either variable is absent, it fails before starting a release build.

GitHub Actions reads `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` from repository secrets and `TAURI_UPDATER_PUBLIC_KEY` from a repository variable. Never put any of those values in workflow logs, commits, or release notes.

## Artifacts and updater manifest

Windows local bundles are written under `src-tauri/target/release/bundle/`: NSIS creates a `-setup.exe` installer and WiX creates an `.msi`. The release overlay additionally creates signed updater artifacts and `.sig` files. Their exact target/architecture names are generated by Tauri and must be checked after a build.

The GitHub release endpoint must publish `latest.json`, the signed NSIS updater installer and signature, plus the MSI installer and signature. Releases that include the MCP companion also publish the self-contained Windows MCP ZIP, portable Node bundle, PowerShell installer, and `SHA256SUMS.txt`. Its static updater manifest uses a SemVer `version`, optional `notes` and `pub_date`, and a `platforms.windows-x86_64` object with the installer `url` and `signature`. Keep the release notes plain text because the desktop settings surface displays them as text.

## Publishing and recovery

The release workflow runs only for a `v<version>` tag whose value matches all three version files. It performs the version check, validates the app and both MCP distributions, creates signed Windows bundles, writes `latest.json`, and publishes a non-draft GitHub Release with `GITHUB_TOKEN` `contents:write` permission.

Treat the private key and password recovery copies as long-lived release-critical material. If either is lost or suspected exposed, generate a replacement pair, update both GitHub secrets and the public-key variable, then ship a higher signed version. Keep the old key protected for historical recovery; do not reuse a compromised key. To roll back a bad release, publish a newer signed repair release—do not retag or replace a version that installed clients may already trust. The stable endpoint follows GitHub's latest non-prerelease release.

Before changing the update channel, verify the public key, endpoint, release assets, signatures, and a prior installed version. Windows publisher signing (Authenticode) is separate from Tauri updater signatures and is not configured here.
